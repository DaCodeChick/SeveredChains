## Conflicts

### C-01 — Fate opcode table differs between engine runtime and recompiler

- **Where:**
  - Severed-Chains `src/main/java/legend/game/scripting/OpType.java` (93 lines, no parameter metadata; `byOpcode` **throws** on unknown opcodes).
  - Script-Recompiler `src/main/java/org/legendofdragoon/scripting/OpType.java` (160 lines, parameter names/directions; `byOpcode` **returns null**; `byName` exists).
- **Discrepancies observed (both `Verified` from source):**
  - The runtime enum carries **no parameter metadata at all** (only `opcode` + `name`, single 2-arg constructor); the recompiler enum records a header param and typed op params per opcode (`OpParam.in/out/both`).
  - The runtime has **no** opcode 100; the recompiler has `NOOP(100, "noop")`.
  - The recompiler records param details for the debug ops that the runtime cannot express: `NOOP_96(96, "debug96", "?", in "?", in "?")`, `NOOP_98(98, "debug98", in "?")`, `DEPTH(99, "depth", out "dest")` vs runtime `NOOP_96(96, "debug96")`, `NOOP_98(98, "debug98")`, `DEPTH(99, "depth")`.
  - `byOpcode` **throws** a `RuntimeException` on unknown opcodes in the runtime, but **returns null** in the recompiler (which additionally provides `byName`).
  - Both agree on the specialization opcodes (`WAIT_CMP_0(4)`, `MOV_0(12)`, `JMP_CMP_0(66)`), and the recompiler documents the specialization rule (`modifyOp`: drop the leading operand when it resolves to 0) — consistent, but the runtime's `byOpcode` is the only runtime-facing decoder.
- **Interpretation at risk:** which table is authoritative for (a) what the runtime interpreter accepts, and (b) what the toolchain emits. Presumably (a) is the runtime table and (b) the recompiler table, and the differences are drift — but opcode 100 and the debug-op param counts need reconciliation against real script binaries.
- **Status:** `Closed (→ research/scripting/02-fate-binary-format.md §6, 2026-11-03)`. M3 resolved the conflict as **drift, with the discrepancies preserved** (not reconciled away): the runtime table is authoritative for execution (it is the only decoder the interpreter uses; unknown opcode → `RuntimeException`), the recompiler table for the toolchain (`byOpcode` → null → the disassembler treats the position as non-code). The full per-opcode reconciliation (67 runtime entries + toolchain-only `NOOP(100)`; counts and the op-89 gap re-verified by the M3 audit) is in scripting/02 §6.1, with the extra discrepancies found along the way: (1) the runtime names but does **not implement** opcodes 5/6/7/11/13/14/15 (named `REWIND*` in both tables; the runtime dispatch `default` throws `IllegalArgumentException` — the toolchain models them as terminal rewinds), (2) div-by-0 (runtime op 33: ±1 rule; toolchain model: `safeDiv` sign rule — the disassembler's symbolic model is wrong for div-by-0 paths), (3) mod-by-0 (runtime: int `ArithmeticException` → crash dump; toolchain model: 0), (4) `CALL` failure modes (runtime null function → permanent `PAUSE_AND_REWIND` stall; toolchain → `UnknownCallException` at compile time). Whether retail scripts ever execute the unimplemented opcodes or opcode 100 is asset-validated-pending (Q-61).

### Scripting (M3)

- **Q-15** — Semantics of opcode 9 (`SWAP_BROKEN`) and of the `_0`-specialized ops (4, 12, 66): original VM quirks, or toolchain conveniences? — `Closed (→ research/scripting/02-fate-binary-format.md §6.1 op 9, §6.3)` — M3: opcode 9 is a **broken swap in the original VM** (the runtime op body copies param0 into both destinations; the reference's own log text says "Broken swap"; both tables model it faithfully — the toolchain's `copyRegister` updates only the second param). The `_0` opcodes are **encoding-compact variants** (first operand constant 0, not stored): 4 = `WAIT_CMP` with left ≡ 0, 12 = `MOV` with source ≡ 0, 66 = `JMP_CMP` with left ≡ 0. The toolchain re-expands them in disassembly and re-compacts them on assembly (`OpType.modifyOp` when the first param resolves to constant 0) — a stable round-trip anchor. Whether retail scripts use them is asset-validated-pending (they are in both tables, so a retail disassembly will show them directly).
- **Q-16** — What does the recompiler `strip` command do (implementation not examined in R0)? — `Closed (→ research/scripting/03-toolchain.md §7.1)` — M3: `strip` applies four transformations in order — (1) cut each line at its first `;` (EOL comments), (2) drop full-line `;` comments, (3) replace every `call Name` whose name matches a metadata method with its **numeric index** (the `call 322` spelling in shipped diffs), (4) trim all lines and drop blanks. The standalone `s` command exposes per-transformation off-switches; the internal strip (used by `genpatch` and the runtime patch pipeline) always applies all four. This canonical form is the coordinate system of every `.diff`.
- **Q-17** — Is the runtime interpreter (`ScriptState`) a faithful model of the original script VM, or a re-derivation? Where might it diverge (e.g., error handling, unknown-opcode behavior — the runtime **throws** per `OpType.byOpcode`)? — `Investigating (advanced by M3)` — M3: the full VM contract is now pinned (research/scripting/05) — frame loop, parse semantics, all 57 op bodies, fork/consume/deallocate, error paths. The reference-specific layer with no established original corroboration is enumerated (scripting/05 §12): crash dump with live disassembly, the `memcpy` OOB catch-and-warn (ported around a documented retail script bug), the `paramCount > 10` guard, the null-function stall as explicit `PAUSE_AND_REWIND`. The `@Method` ROM addresses are the only original-VM anchor; per-op parity (float handling, shift semantics, zero-division rules) remains unverifiable without the PSX binary. Owner: M4/T-COMPAT + M9.
- **Q-18** — What are the round-trip stability conditions for decompile→compile, and what invariants do the 300+ shipped script patches depend on? — `Closed (→ research/scripting/02-fate-binary-format.md §8, 03-toolchain.md §10; hazard set extended by the M3 audit)` — M3: byte-stable round trip holds iff (1) the entrypoint-count inference matches (or is pinned), (2) no inline pointer is out of range (rewritten to 0 with a warning), (3) no param uses a one-way type (0x0c/0x0d/0x11/0x17 → reparse failure; **0x24–0x27 → reparse failure** — the translator emits absolute `stor/var/reg/inl[inl[0xADDR]]` forms with no tokenizer pattern; 0x12/0x15/0x16 → decompile failure) or 0x13 (re-emitted as 0x09 — value-stable, byte-changing) or a colon-less 0x21 registry ID, (3b) no compare op carries **header 8/9** (`cmp &&`/`cmp ||` — the translator renders `Unknown CMP operator N` on all compare ops incl. CMP itself; both new hazards experimentally confirmed by the M3 audit), (4) jump-table lengths are stable (pinned by shipped `table_length` configs; 10 observed), (5) labels are referenced by name only. Patches are unified diffs over the stripped/label-reindexed/call-indexed decompilation of the **pristine backup**; the in-game pipeline is idempotent (CRC32 change detection incl. include closure, backup→restore self-healing, cache = structural mirror of the patches dir).
- **Q-19** — Remote scmeta (`legendofdragoon.org/scmeta/`) vs local `patches/meta/*.csv`: which is authoritative, and are they currently in sync? (Remote not fetched during R0 — no network assumption made.) — `Closed (→ research/scripting/04-meta-system.md §5.2)` — M3 (no network used, per project constraint): the **local** `patches/meta` CSVs are the authoritative in-game metadata — `ScriptManager.meta()` constructs `MetaManager(null, patchDir).loadMeta("meta")`, and the `baseUri = null` + existing-local-dir path means **no network code executes** in the runtime; the remote service (named versions + uncached `snapshot`) is wired only into the standalone `Shell`. Sync state of the two copies is uncheckable offline (Q-62); the load-bearing invariant is row order (descriptions.csv row = call index), which the local CSV preserves against the runtime tables (verified 592/592 in scripting/06).

- **Q-40** — Input sampling timing: the original polled the pad inside its frame body; the reference samples via SDL between frames (input tick before render tick) and dispatches action events to the engine state during the input tick. Behavioral consequences (e.g., same-frame input→state visibility differences) not fully characterized. — `Open` (low) — M9 — needs: retail action inventory + edge-case audit (input on the same frame a state changes).
- **Q-41** — ~~SPU control-word data race~~ — `Closed (corrected by audit F-02, 2026-11-02)`: **no race exists.** The R1 observation ("`Spu.keyOn/keyOff` written from the main thread without synchronization") was a misread: `keyOn`/`keyOff` and *every* other SPU control method (volumes, reverb, noise, mute) are `synchronized(Spu.class)` (Spu.java:402-414 and throughout), and `Spu.tick()` (Spu.java:85) holds the same monitor, consuming and clearing the edge words under it. The only unsynchronized SPU write is `setPlayerVolume` (a float). The "unsafe corner" entry was removed from architecture/03 §5. The edge-trigger contract (level words OR-accumulated by control, consumed and cleared once per tick) remains what a reimplementation must preserve.
- **Q-42** — `ScriptManager.tick()` sets `this.upperBound = 9` every frame (ScriptManager.java:219) — purpose of the upper-bound in script ticking? — `Closed (→ research/scripting/05-runtime-interpreter.md §2, 2026-11-03; mechanism wording corrected by the M3 audit)` — M3: slots **0–8 are hard-reserved** — `findFreeScriptState()` scans only 9–107 (both loops start at ≥ 9; the wrap value is 9), so auto-allocation can never return 0–8; those slots are taken only via explicit-index allocation (observed: 0 = submap controller, 1 = lighting controller, 5 = battle script DRGN1.401, plus game-data-driven player BENT slots). **Corrected mechanism**: allocation is **round-robin** over 9–107 from the last allocation point (`findFreeScriptState` pre-increments `upperBound`, wrap ≥108 → 9); the per-tick `upperBound = 9` reset makes the first allocation of a frame start scanning at slot **10**, so slot 9 is returned only when slots 10–107 are all occupied — a round-robin allocation pointer, not lowest-free-first as the M3 text stated.
- **Q-43** — Async file-load failure propagation: most `Loader`/`DrgnFiles` CompletableFutures have no observed failure handler; a failed load surfaces as an uncompleted future / `CompletionException` at await sites (`Inferred`). — `Closed (→ research/assets/01-iso-and-file-tree.md §6.2-6.3)` — M2: the full contract is source-verified: `onFileLoadingException` (Loader.java:143-146) logs and **completes with `null`** for files and directories alike; the ROM's script-facing wait is `DrgnFiles.scriptWaitForFilesToLoad` (`@Method(0x80017564L)`), which returns `PAUSE_AND_REWIND` while `Loader.getLoadingFileCount() > 0` — combined with frame-top script execution, a script never observes a partially-loaded resource set, and a failed load is observed as an **absent asset** (`null`), never a torn one. Sync variants (`loadFileSync` etc.) throw `RuntimeException("Failed to load file …")`.
