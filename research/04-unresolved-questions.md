# Unresolved Questions and Research Risks

Register of open questions, known conflicts, and research risks. Maintained continuously; entries are closed by pointing to the evidence that resolved them (never deleted). Status values: `Open` / `Investigating` / `Closed (→ doc)`.

## Conflicts

Disagreements between repositories (or between a repository and external expectations) that must be investigated rather than silently resolved.

### C-01 — Fate opcode table differs between engine runtime and recompiler

- **Where:**
  - Severed-Chains `src/main/java/legend/game/scripting/OpType.java` (93 lines, no parameter metadata; `byOpcode` **throws** on unknown opcodes).
  - Script-Recompiler `src/main/java/org/legendofdragoon/scripting/OpType.java` (160 lines, parameter names/directions; `byOpcode` **returns null**; `byName` exists).
- **Discrepancies observed (both `Verified` from source):**
  - The runtime enum carries **no parameter metadata at all** (only `opcode` + `name`, single 2-arg constructor); the recompiler enum records a header param and typed op params per opcode (`OpParam.in/out/both`).
  - The runtime has **no** opcode 100; the recompiler has `NOOP(100, "noop")`.
  - The recompiler records param details for the debug ops that the runtime cannot express: `NOOP_96(96, "debug96", "?", in "?", in "?")`, `NOOP_98(98, "debug98", in "?")`, `DEPTH(99, "depth", out "dest")` vs runtime `NOOP_96(96, "debug96")`, `NOOP_98(98, "debug98")`, `DEPTH(99, "depth")`.
  - `byOpcode` **throws** a `RuntimeException` on unknown opcodes in the runtime, but **returns null** in the recompiler (which additionally provides `byName`).
  - Both agree on the specialization opcodes (`WAIT_CMP_0(4)`, `MOV_0(12)`, `JMP_CMP_0(66)`), and the recompiler documents the specialization rule (`modifyOp`: drop the leading operand when it resolves to 0) — consistent, but the runtime's `byOpcode` is the only runtime-facing decoder.
- **Interpretation at risk:** which table is authoritative for (a) what the runtime interpreter accepts, and (b) what the toolchain emits. Presumably (a) is the runtime table and (b) the recompiler table, and the differences are drift — but opcode 100 and the debug-op param counts need reconciliation against real script binaries.
- **Status:** `Open`. Owner: M3 (T-FATE-BIN). Needs: disassembler's opcode reading code + at least one real script binary (or the patches' decompiled texts) to confirm whether opcode 100 or the debug-op params ever appear in practice.

### Platform and lifecycle (M1)

- **Q-01** — How exactly does `RENDERER.run()` drive the per-frame game loop? — `Closed (→ research/platform/02-execution-model.md §1-2)` — R1: `RENDERER.run()` → `PLATFORM.run()` while-loop ticking registered `Action`s; the window's render `Action` (created in `SdlWindow` ctor, 60 Hz default, rescheduled by `setFpsLimit`) runs `tick()` = `SDL_GL_SwapWindow` → `events().onDraw()` → `clearPressed()`; the `onDraw` handler (registered in `RenderEngine.init`, RenderEngine.java:586) runs the frame and invokes `renderCallback`, which `bindRendererEvents` (Scus94491BpeSegment.java:215) sets to `gameLoop`. No vsync (swap interval 0); pacing is the software Action timer with catch-up tick skipping.
- **Q-02** — Which thread(s) call `SPU.tick()`? — `Closed (→ research/platform/02-execution-model.md §6)` — R1: a dedicated **"SFX" thread** started by `Audio.startSound()` (transition-to-game) runs `soundLoop()` at 60 Hz (`NANOS_PER_TICK = 1e9/60`, catch-up skip after 3×), calling the game `Sequencer.tick()` (BGM state machine) and `SPU.tick()` (24-voice model) each tick; the SPU's OpenAL source is consumed by the 120 Hz OPEN_AL thread. The SFX thread catches `Throwable` per tick (un-killable by design).
- **Q-03** — What is `FUN_80020ed8`? — `Investigating` (mechanism resolved; consumer-side effects outstanding) — R1: fully read (EngineStates.java:99-143). Per frame: resets `submapFullyLoaded_800bd7b4`; on engine-state change, sets the submap-transition-mode global `_800bd7b0` (2 = normal entry, 9 = from title, -4 = from battle + `transitioningFromCombatToSubmap`, 3 = from world map) and the one-shot title-origin flag `_800bd7ac` (consumed by `FUN_800218f0`, which re-sets `_800bd7b0 = 9`). `_800bd7b0` is script-visible as game variable 67 (`GameVarParam.java:155,303`). Remaining: how SMap consumes these transition modes (M9).
- **Q-04** — Is the base 30 Hz rate original or a reference choice? — `Closed (→ research/platform/02-execution-model.md §5)` — R1: the decompiled ROM code itself sets `vsyncMode_8007a3b8 = 2` in `gameInit`/`preload` (Scus94491BpeSegment.java:624,640) and changes it per state (battle → 3 = 20 Hz: Battle.java:2040,2361; battle end → 2: Battle.java:2578; battle transition → 1 = 60 Hz: SBtld.java:359; title/game-over → 2; scripts can write it as game var 25: GameVarParam.java:245). The per-state frame-rate structure is therefore **original, `Verified`**; `tickMultiplier()` (default 2, WMap/Battle override) records original per-state rates for text cadence and is *not* a rate driver. Timestamp unit = 1/60 s game time, advanced by `vsyncMode` per frame when `advancesTime()` (advance mechanism `Verified`; the 1/60 s unit interpretation is `Inferred`). **Audit F-01 (2026-11-02) correction to the R1 census:** SMap (SMap.java:4088), WMap (WMap.java:681, 707) and Credits (Credits.java:239) each set `vsyncMode = 1` (60 Hz) in their contexts — exploration (submap/world map) and credits run at **60 Hz**, not 30 Hz; 30 Hz is the title/game-over/wmap-screens/transition rate. The full corrected write-site census is in platform/02 §5; the core conclusion (the rates are the ROM's own, `Verified`) stands.
- **Q-05** — Updater remote and protocol? — `Closed (→ research/platform/01-application-lifecycle.md §1, §3)` — R1: `Updater` (legend/core/Updater.java) GETs `https://api.github.com/repos/Legend-of-Dragoon-Modding/Severed-Chains/releases` asynchronously (10 s connect timeout), filters releases by channel tag (`Version.CHANNEL` or `release`) with `updated_at` after the build timestamp, picks the newest; platform asset URL chosen by OS/arch keyword (Windows / MacOS_M1 / MacOS_Intel / Linux_ARM64 / Linux, excluding Steam_Deck). Skipped for timestamp-less (IDE/custom) builds. The downloaded artifact is a new `updater.jar`, staged as `updater.jar.new` and swapped in at the next process start (Main.java:51-66). Update *content* is fetched/applied by the updater itself (not inspected in R1; the main repo only surfaces the release to the user via the loading screen / title options).
- **Q-06** — Full per-frame phase contract (invariants per phase)? — `Open` — R1 documented the complete *ordering* (platform/02 §2-3) but not per-phase invariants (what each phase may mutate). Needs: systematic call-site audit (M10 or M5).
