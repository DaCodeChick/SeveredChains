## 2. The battle command menu

### 2.1 Actions are a moddable registry (U1)

A menu action is a `BattleAction` (`BattleAction.java:19`) — a `RegistryEntry` (M8-02) with three overridable methods: `use(Battle, PlayerBattleEntity)` (default `CONTINUE_SCRIPT`), `tick(Battle, PlayerBattleEntity)` (per-frame callback once an action is in flight; `IGNORE` / `CONTINUE_SCRIPT` / `REPEAT_TURN`), and `draw(Battle, iconIndex, selected)`. The retail menu is assembled from the registry in `LodMod` (`battleactions/`): `RetailBattleAction` (the plain icon base: icon quad from a fixed texture atlas, 4 icon states `{0, 1, 2, 1}`, label text under the selected icon) and the specific retail actions; `SeveredBattleAction` is the reference-added base for extra (non-retail) actions. **The menu bar is not hardcoded** — `scriptOverrideBattleMenuActions` (Battle.java `:4129`, @ 0x800cca34, same method address as the menu bridge — the reference shares the slot) replaces the action list from a registry-ID array, which is the mod surface for battle menus (M8-03).

`TransformAction` (retail, `super(2)` — icon slot 2) carries one interactive behavior: while the transform icon is selected, UP/DOWN cycles `player.detransformationMode` (the `DetransformationMode` enum `NOW`/`AFTER_TURN`, default `NOW`, `PlayerBattleEntity.java:102`). The only writer of that field in the engine is this menu action (`TransformAction.java:46/48`); no native code changes it (grep-verified). In vanilla play it therefore stays `NOW` unless a mod/registry action touches it — the `DETRANSFORM_FROM_DRAGOON_AFTER_TURN` script path (05b §7.8, mode 1) is reachable through this UI (retail-anchored: the up/down selection is a retail LoD behavior).

### 2.2 Input → action (L3)

`BattleHud` menu state (`whichMenu_800bdc38` + `battleMenu_800c6c34` `BattleMenuStruct58`): while in the "checking for input" state (`case 1`, `BattleHud.java:1490+`):

Retail LoD has a single cursor over the icon bar; the per-button bindings are a reference convenience (U2).
- **Cursor + confirm** (retail model, `:1615`): `INPUT_ACTION_MENU_CONFIRM` uses `battleMenu.actions.get(selectedIcon_22)` — the selected icon.
- Left/Right held (`:1537`/`:1566`) moves the selection with a highlight animation (states 2/3: stepped highlight travel + fade, `countHighlightMovementStep_30`, `colour_20`… `:1621–1660`); camera position switching is state 4 (`cameraPositionSwitchTicksRemaining_44`, `:1643`).
- `useAction` (`:1689`): `isIconEnabled` gate (disabled → menu sound 40) → `action.use(battle, player)` (`FAIL` → sound 40, null) → sound 2 → `PAUSE_SCRIPT` → null (the action owns the flow via `tick`) → otherwise returns the action, which the HUD stores as `battleMenu.currentAction`.
- The OPTIONS input (`:1495`) pushes a `BattleOptionsCategoryScreen` (config UI, M7) onto the menu stack and closes the battle menu on save.

### 2.3 The native bridge: `scriptSetUpAndHandleCombatMenu` (L3, @ 0x800cca34)

This is the single script-facing menu function (table slot 160, 05a §7). Per call (Battle.java `:4083–4127`):

1. If a list menu is open (`hud.listMenu_800c6b60 != null` — the item/spell pick list, M7 menu stack) → `PAUSE_AND_REWIND` (the calling script parks; the HUD keeps rendering).
2. If `battleMenu.currentAction != null` → `currentAction.tick(battle, player)`: `IGNORE` → keep parking; `CONTINUE_SCRIPT` → `CONTINUE` (action finished); `REPEAT_TURN` → clear `currentAction`, `PAUSE_AND_REWIND` (the turn repeats — the action failed or was cancelled).
3. If the script state has `FLAG_RELOAD_BATTLE_ACTIONS` (0x1000) → `hud.initializeMenuIcons(scriptState)` — rebuild the icon set (the script ORs 0x1000 into its flag word `stor[7]` before/after transformations, `or 0x1000, stor[7]` in `ACTION_SPECIAL`/`ACTION_TRANSFORM` — the menu rebuilds for the new dragoon/normal form) and clear the flag.
4. `hud.tickAndRender()` → the selected action (or null). Null → `PAUSE_AND_REWIND` (wait for the player — this is the parking loop the script spins on between turns).
5. Action selected → out-param `params_20[0] = currentAction.getRegistryId()`. **The script receives the registry ID, not an index** (U3).

### 2.5 Action repeat and the tutorial/counter words (U4, U5, U31)

`LABEL_515` (`:4747`, after every action — verified verbatim):

```
if var[45][243] == 0 → return
if var[45][253] == 0 → return
if var[45][242] != 2 → var[45][243] -= 1
if var[45][243] == 3 → return
var[45][243] -= 1
```

- `var[45][253]` — the **repeat-available mask**: cleared to 0 at the start of the menu wait (`LABEL_63` `:578`), set to 0xffffffff at the end of dragoon actions (`LABEL_64` `:583`, called from the epilogues of `ACTION_TRANSFORM`/`ACTION_DRAGOON_ATTACK`/`ACTION_SPECIAL`). Verified.
- `var[45][243]` — **not a script-managed budget** (U31). It is `battleState_8006e398._54c` (`GameVarArrayParam` case 243) — the word the **retail tutorial-fight handler** owns: the decompiled native handler (`LodMod.java:759–787`, in-source comment: "This seems to be for the tutorial fights - disables all actions except for one") disables all menu actions while `_54c != 0`, re-enables one per tutorial step (ATTACK at `_548 == 0`, ITEMS at `_548 == 1`, ATTACK at `_54c == 3`, TRANSFORM at `_54c ∈ {5, 9, 16}`, D_ATTACK at `_54c == 12`, SPELLS otherwise), sets the tutorial enemy's `FLAG_TAKE_FORCED_TURN`, and increments `_54c`. In a normal battle it is 0 (the battle state is freshly constructed at battle init — `Battle.java:2588` — and no normal-battle writer exists in the reference). Separately, the **retail d-attack script loads the word** (`mov 0x9, var[45][243]` — the value into scratch word 9) in its counter-attack branch (DRGN1 `254.diff` context lines — retail code, unmodified by the patch, §4.6). The L4 player script *reads* the word as a "0 = normal" gate (mastery tick and SP-halving, §4.4) and decrements it in `LABEL_515` when the repeat mask is set — in the reference that decrement can only act during a tutorial fight (243 ≠ 0) after a dragoon action (253 ≠ 0).
- `var[45][242]` — `battleState_8006e398._548` (`GameVarArrayParam` case 242) — the **retail tutorial-type word** (native handler: 0 = attack tutorial, 1 = item tutorial; the higher stages are driven by `_54c`'s value). **Never written by the reference** — the L4 script only reads it (the `== 2` gates: the post-addition block §5, the main-loop dragoon-SP skip `:4596`, the `LABEL_515` sub-check, the `ACTION_TRANSFORM` epilogue `:5151`), and the native code only reads it (`LodMod.java:766/770`). The retail script (binary, unavailable) presumably wrote 0/1/2… for its tutorial stages — the L4 `== 2` gates are **vestigial and never satisfied in the reference** (U31).

Consequence for forced turns (U5, corrected): the L4 script's only two flag-word `0x20` writes (both in the post-addition block, §5) sit behind the never-satisfied `242 == 2 && 243 == 3` gate, so **in the reference the acting dragoon never self-sets `FLAG_TAKE_FORCED_TURN`** (the runtime mirrors the script flag word's 0x20 bit onto the acting bent — `ScriptState.java:106` — but nothing in the live L4 path sets it). The only live forced-turn sources in the reference's battle are the native tutorial handler (`LodMod.java:768/772/785`) and the retail d-attack DEFF script's counter branch (target's flag word, §4.6). Whether the retail "a dragoon keeps acting while it has SP" behavior in dragoon space was carried by the post-addition block (its 242/243 gate values) is `Inferred` — the retail script is unavailable (open item §15).

### 2.6 Targeting (L3)

`handleTargeting(targetType, targetAll)` (`BattleHud.java:1824`, @ 0x800f7768), called from the list-menu/arrow flow (the script side enters it via the item/spell/item-throw flows, 05b §5/§7):

- CONFIRM → return 1 (accept; `target_48` = the target's script index, `combatantIndex_54` = slot or −1 for "all", `displayTargetArrowAndName_4c` off, `targetArrowHiding` on); BACK → return −1 (cancel, `target_48 = −1`); else 0 (still targeting).

## 3. Action execution (script-side flows)

2. `LABEL_346` (approach/camera setup), read attacker/target positions, `var[44] = 0x22` (camera index).

### 3.2 Guard, escape, confused, attack-ally

- **`ACTION_GUARD`** (`:4770`): set the `GUARD` stat (bit 0), the guard animation 0x5, the `GUARD_HEAL` stat is consumed by `START_TURN` (05b §7.2); on a successful guard the HUD shows the guard text. The `GUARD` word also gates the on-hit guard animation in `APPLY_DAMAGE` (05b §4.7).
- **`ACTION_RUN_AWAY`** (`:4961`): the escape roll (05b §7.5: `escapeChance` × `simpleRand` pipeline, `runAwayFlags_2b4`), success → `scriptSetPostBattleAction` (the escape exit, 05a §8); failure → a "cannot escape" text and the turn is consumed.
- **`ACTION_CONFUSED`** (`:5342`): `rand 100` → roll `< 0x14` (20) → `ACTION_GUARD`; roll `< 0x3c` (60) → `ACTION_RUN_AWAY`; else → `ACTION_ATTACK_ALLY`. So a confused character: 20% guard, 40% flee, 40% attack an ally (U8).
- **`ACTION_ATTACK_ALLY`** (`:5350`): 10-frame wait; pick a random *living* ally via `rand var[51]` (alive-player count) mapped through the `var[50][i]` alive-bent table; look-at, sound 0xb, attack wind-up animation 0x10; **damage = target.MAX_HP / 5** (20% of max HP, `:5375`); if the target is self → `fork_reenter(self, 2, damage)` (entry point 2 = `ENTRYPOINT_2_TAKE_DAMAGE`, `:5494`: targeting-bit set/clear around `APPLY_DAMAGE`), else direct `APPLY_DAMAGE` with `stor[32] = damage`; a post-hit reaction (entry point 4 = `ENTRYPOINT_4_HANDLE_DEATH`, `:5829`) fires if the target's `var[128+slot][7] & 0x400`. Ally damage goes through the full incoming pipeline — shields, guard, the fear ×2, and death all apply (U9).

## 4. The addition (timing overlay) system

### 4.1 Data model (completing 05b's `AdditionHitProperties10`)

`Addition` (abstract, registry) → `SimpleAddition` (the retail base): `countsTowardsMastery` (bool — whether the addition earns mastery), `LevelMultipliers[]` (per level: `damage` and `sp` float multipliers), `AdditionHitProperties10[] hits`:

- `getDamage` = `int( Σ hits[i].damageMultiplier_04 × levelMultipliers[level−1].damage )`
- `getSp` = `Σ (int)( hits[i].sp_05 × levelMultipliers[level−1].sp )` (per-hit truncation)
- `getXpToNextLevel` = `level × 20`; `getMaxLevel` = `levelMultipliers.length`; `isComplete` = `level >= max`; `getHitCount` = `hits.length`
- Data census (`LodAdditions.java`, source-verified): additions have 2–8 hits; **the final hit always has `isFinalHit_07 = 4`** (all other hits 0); the first hit of the ultimate additions (`blazing_dynamo`, `flower_storm`, `omni_sweep`, `perky_step`, `bone_crush`) has `flags_00 = 0xe0` (all others `0xc0`); level multipliers range 1.0–1.5 (damage) and 1.0–1.45 (SP), 4–5 levels per addition.
- `BattlePreloadedEntities_18cb0.getHitCount(charSlot)`: if the bent is dragoon (`FLAG_DRAGOON`) → `dragoonAdditionHits_38.get(charSlot).hits_00.length` (the d-attack hit table), else the registry addition's hit count. The 20-byte retail form (`AdditionHitProperties20`) is the byte form's counterpart (same fields, shorts).

**`AdditionHitProperties10` `get(index)` map** (`AdditionHitProperties10.java`, the indices the script reads via `scriptGetHitProperty`): 0 `flags_00`, 1 `totalFrames_01` (hit length; normally `offset + success + 1`), 2 `overlayHitFrameOffset_02` (frames until the press is due), 3 `totalSuccessFrames_03` (window width), 4 `damageMultiplier_04`, 5 `sp_05`, 6 `audioFile_06`, 7 `isFinalHit_07`, 8 `cameraMovementX_08`, 9 `cameraMovementZ_09`, 10 `cameraMovementTicks_0a`, 11 `hitDistanceFromTarget_0b` (pushback), 12 `framesToHitPosition_0c` (approach speed; javadoc: only the first hit's value has an effect), 13 `_0d` (32 except some Haschel entries; unused in the reference), 14 `additionFailAnimationIndex_0e` (non-zero → the miss animation), 15 `overlayStartingFrameOffset_0f` (spinner start delay), 100 `animationScale` (default 100), 16+ sounds (even = `soundIndex`, odd = `initialDelay`; out of range → `NO_SOUND (−1, 0)`).

### 4.2 The spinner engine — `AdditionOverlaysEffect44` (L3)

Allocated by `SEffe.scriptAllocateAdditionOverlaysEffect` (@ 0x801077e8): `allocateEffectManager("Addition overlays", scriptState, new AdditionOverlaysEffect44(attacker, target, autoCompleteType))`, then **`state.setStor(8, 0)`** — "storage for counterattack state" (the script/deff writes non-zero here to arm the counter window, §4.6), `additionOverlayActive_80119f41 = 1` (script-visible via `scriptGetAdditionOverlayActiveStatus(0)`, §4.2/§6).

**Layout** (44 bytes + per-hit array): `attackerScriptIndex_00`, `targetScriptIndex_04`, `count_30` (ubyte), `pauseTickerAndRenderer_31` (0 render+tick, 1 skip both, 2 render only), `additionComplete_32` (byte), `currentFrame_34` (short), `unused_36` (ushort = hit 0's start offset), `numFramesToRenderCenterSquare_38`, `lastCompletedHit_39`, `autoCompleteType_3a` (0 normal, 1 auto-complete on miss, 2 WC+UW auto-complete, 3 tutorial 2-hit array), `hitOverlays_40[]` (`AdditionOverlaysHit20`: window bounds, 17 `AdditionOverlaysBorder0e` borders, `isCounter_1c`, shadow colour), plus the **static** `additionHitCompletionState_8011a014` (byte array, re-allocated per effect: `hitCount + 1` entries).

**Hit-count arithmetic** (U13): `hitCount = getHitCount(charSlot, autoCompleteType) − 1` (autoComplete 1/3 → the 2-entry tutorial array); `count_30 = hitCount`; the per-hit overlay array has `count_30` entries and the completion-state array has `count_30 + 1`. For an N-hit addition the engine therefore allocates timing windows for the **first N−1 hits only; the final hit (`isFinalHit_07 = 4`) has no window and is automatic** — the script's per-hit loop (§4.3) iterates the timed hits and synthesizes the completion of the rest. (The retail script text is unavailable; this is the engine-side invariant, and the data census shows the final hit is always the un-timed one.)

**Per-hit window computation** (constructor `:101–170`): running `overlayDisplayDelay` starts at hit 0's `get(15)`; per hit: `lower = delay + 2`; `totalHitFrames = get(1)`; `beginDisplay = get(2)`; `success = get(3)` (**scaled by `ADDITION_TIMING_WINDOW_CONFIG`** — the L4 "increase timing window" multiplier, logged); `target = lower + beginDisplay`; **`lowerBound = target − success/2 + 1`**, **`upperBound = target + success − success/2`** (integer division — the window is `success` frames wide, biased one frame earlier); `delay += totalHitFrames`. The 17 borders per hit: 14 rotating squares (sizes `(18−val)×10×1.5×scale`, `val` 16→3, angles `(16−val)×11.25°` — zeroed when `REDUCE_MOTION_FLASHING_CONFIG` is set, 5 visible frames each, staggered around the window) + 3 static inner squares (sizes 30/28/26 × 1.5 × scale, 17 visible frames, the fade side-effects −1/1/0). Colours from `additionBorderColours_800fb7f0` (12 RGB values, 4 palette entries; initial index 3 = addition white; entries 2/3 = the counter/orange colours, overridden by `Config.changeAdditionOverlayRgb()` when enabled). Size scaled by `ADDITION_OVERLAY_SIZE_CONFIG`.

**Tick** (@ 0x801073d4): skip if `pauseTickerAndRenderer_31 == 0` is false… (i.e. when it is 0): `currentFrame_34++`; per hit: **if `currentFrame == upperBound + 1` and the state is still 0 → state = −2 (too late)** + `propagateFailedAdditionHitFlag` (all later hits inherit the same state, their windows zeroed, `additionComplete_32 = 1`); if any un-attempted hit remains → not failed. Per-hit border countdown (`tickBorderDisplay`: on failure the borders fade 0x20/frame and hide at zero; shadow decays 3/frame). When no borders remain and `additionComplete_32 != 0` → **`additionOverlayActive_80119f41 = 0`, `state.deallocateWithChildren()`** (the script observes completion via `scriptGetAdditionOverlayActiveStatus(0) == 0`, `LABEL_61` `:569`).

**Input** (from `currentFrame >= 9` — input unlocks 9 frames in): find the first un-attempted hit; **counter arming**: `AdditionCounterAmount` config ≠ NONE and the effect state's `stor[8] != 0` → `isCounter_1c = true`, `stor[8] = 0` (consumed); then, unless auto-completing: correct button = `INPUT_ACTION_BTTL_ATTACK` (or `INPUT_ACTION_BTTL_COUNTER` when counter-armed), wrong = the other; **press before the window → −1 (too early); wrong/both → −3 (wrong button); right button inside the window → 1 (success)**, `hitSuccessful_01 = true`; any negative state propagates the failure; `numFramesToRenderCenterSquare_38 = 2` (the 2-frame center-square flash: white on success, grey on early, the counter colour on a too-late counter, the border colour on a too-late normal). Auto-complete (type 1/2): the press is simulated automatically at the window.

**Render** (@ 0x8010726c): borders (only when `ADDITION_OVERLAY_CONFIG == FULL`), the button-press hint (the ATTACK/COUNTER glyph + arrow, "up" position ≥2 frames before the window, "down" + glow otherwise), and the center solid square during the window (state −2 preview) and after completion.

**`scriptAlterAdditionContinuationState`** (@ 0x801078c0): state 0 → toggle `pauseTickerAndRenderer_31` between 0↔1 (the source comment: "occurs when counterattack counter is successful; have not gotten other conditions to trigger"); state 2 → toggle 0↔2 (render-only — the ultimate-addition hold, §3.1); other → `setContinuationState(state)`: `additionComplete_32 = state` and **all remaining hits get state −1 with zeroed windows** (the script ends the addition early — used at `:1246`/`:1283`/`:1298`, e.g. when the target dies mid-addition).

### 7.2 The tick word model (05b §8.3 item 2, completed)

`var[45][129+slot]` (the `Status04` pack, `GameVarArrayParam` cases 129–136) is a 32-bit word with (all script-managed — **no native code ticks it**, 05b):

- **bits 0–2**: the ailment index (0 petrified … 7 poisoned);
- **bit 0x80**: "active" (the 3-turn driver is live) — set by entry point 11 (path A: `or 0x80` at `:3908` after confirming the ailment is not already active) or by path B (0x380 initial);
- **bit 0x40**: "this-turn tick pending" — set by `LABEL_466` (`:4644`) at each turn start **if 0x80 is set**, consumed by the per-ailment ticks;
- **bits 0x100/0x200 (and up to 0xf00)**: the turn countdown — path A starts at 0x300 (two 0x100-units); each turn's tick (`LABEL_475` `:4466`, called from the per-ailment ticks `JMP_ad94_1..5`): if 0x40 is set: `word −= 0x40`, `word −= 0x100`; if the pre-decrement high nibble (`and 0xf00`) was 0 → `word = 0` (force-clear). When the high bits reach 0 the word's 0x80 is eventually cleared (word = 0) and the driver ends (§7.3). **`UNSTUN_WHEN_DAMAGE_IS_TAKEN`** (`:545`, called from `APPLY_DAMAGE` `:5819` and `APPLY_DAMAGE_SIMPLE` `:5812` when damage > 0 and the bent survives): if `var[45][224] > 0` (damage was dealt) and `STATUS & 0x10` (stunned): **`word |= 0xf00`** — the high nibble becomes 0xf00, which the driver's termination check (`word & 0xf00 == 0xf00`, `LABEL_448` `:4032`) treats as "turns exhausted" → **stun ends early when the stunned character takes damage** (U22).

## 8. Post-battle actions and screens

### 8.1 Dispatch (L3 + registry)

`scriptSetPostBattleAction` (Battle.java `:4293` @ 0x800ccf0c, table slot 170; the boss-kill variant 172 `:4284`): the first argument is a registry ID when `getRegistryId()` resolves, else a legacy int (1 = VICTORY, 2 = GAME_OVER, 3 = BOSS_KILL, 4 = FMV, 5 = MERCHANT — the param docs); the registry path is `REGISTRIES.postBattleActions.getEntry(id).get()` (M8-02: `PostBattleActionRegistry`, `RegisterPostBattleActionsEvent`); the instance is stored in `postBattleAction_800bc974` (with the script's params) and the call returns **`PAUSE_AND_REWIND`** (the script parks; the battle takes over). The retail variants: `VictoryPostBattleAction`, `GameOverPostBattleAction`, `PlayFmvPostBattleAction`, `BossKillPostBattleAction`, `MerchantPostBattleAction`, `DiedInArenaFightPostBattleAction` (each an `AbstractPostBattleAction` with `getTotalDuration`/`getFadeDuration`/`performAction`, the per-action text and music).

### 8.2 The exit flow (L3, 05a §8 completion)

`battleTick` (`:2360`): while `postBattleAction != null` → increment the loading stage and return (the normal battle tick is skipped); the camera fadeout (`onCameraFadeoutStart` → fade → `onCameraFadeoutFinish`, 05a) plays over the action's duration; completion when `currentPostCombatActionFrame >= getTotalDuration()` **or** (button press and frame ≥ 25) → `startFadeEffect(1, getFadeDuration)` → `performAction(this)` (per-action: victory → music + the submap hand-off; game over → the `GameOver` title path (M9-02 T10); FMV → `VideoPlayer` takeover; boss kill → the encounter's `postCombat` data; merchant → the shop screen) → `updateGameStateAndDeallocateMenu` → `submapScene_80052c34`/`submapCut_80052c30` from the encounter → `EngineStates.SUBMAP`.

### 8.3 The post-battle screen (L3, `PostBattleScreen.java`)

- **XP** (`pendingXp_8011e180`): at battle end, per character: `totalXpFromCombat_800bc95c / xpDivisor` (05a §8 reward model); secondary (non-active) characters get `safeDiv(total, divisor) × secondaryCharXpMultiplier`. Distribution (`:522`): per confirm press (or when the remainder < 10) **`capped = min(pending, 10)`** — the classic 10-XP-per-press loop; `character.xp += capped` (level-ups fire through the normal level-up path, M9-06).
- **SP → dragoon XP** (`:561`): `spGained_800bc950` — accumulated by **`scriptGiveSp`** (Battle.java `:487`: `sp.current += amount; spGained.mergeInt(character, amount)` — every script SP grant, including the additions' §4.4 grants, is banked here) — is converted with the **same 10-per-press pattern** into `character.dlevelXp_0e` (dragoon level XP), then the **dragoon level-up loop** (`:588`): `while dlevelXp >= getDxpToNextLevel() && dlevel < MAX_DRAGOON_LEVEL (config)`: `applyDragoonLevelUp(levelUpActions)`; the gains are banked in `dragoonLevelsGained_8011e1d8`.
- **Unlocks** (`checkForUnlocks` `:602`): per character, `template.checkUnlocks(character, actions)` (M8-03: the `AdditionUnlockCriterion`/`SpellUnlockCriterion` registry criteria — level, mastery, spell-dragoon, etc.) → `applyLevelUpActions` (`:614`): `UnlockAdditionLevelUpAction` → `additionsUnlocked` (shown on screen), `UnlockSpellLevelUpAction` → `spellsUnlocked`; the addition level-up event (`PostAdditionLevelUpEvent`, `:174`) fires for mod listeners (M8-02).
- **Mastery**: the addition `xp++` ticks (§4.4) are consumed by the `AdditionMasteryUnlockCriterion` in `checkForUnlocks` — the post-battle screen is where mastery converts to unlocks (M9-06 covers the criterion internals).

## 11. RNG and timing determinism

- **No RNG in the spinners**: both addition engines are pure frame counters (`currentFrame_34`, `baseAngle_02` + the step-count tables) — given the same start frame and inputs, the outcome is deterministic (U26).
- **RNG in this surface**: `ACTION_CONFUSED` (20/40/40, `rand 100`), `ACTION_ATTACK_ALLY` (target pick, `rand var[51]`), the `LABEL_260` electricity-effect child (`scriptRand` calls, presentation only) — all on the `simpleRand()` 16-bit LCG (M4-05 §2.3; 05a §9). The addition accuracy roll itself is the native `scriptCheckPhysicalHit` (05b §5.1). The d-attack timing has no RNG (the daddy meter is deterministic; the *sight-appear* condition in the retail d-attack script is unknown — §15).
- **Timing**: the spinner input unlocks 9 frames into the effect (§4.2); the dragoon meter's pre-press window is `ticksUntilStart` ticks (§6.1); the addition frame budget is `var[45][86]` (§4.3). All are VPS-based frame counts (M4/M5), so determinism holds per the 05a timing model.
