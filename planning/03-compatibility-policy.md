# P0-05 — Compatibility Policy Architecture (Revised)

Status: **Revised (2026-11-15).** Supersedes the framework half of the 2026-11-14 draft ("P0-03 — Compatibility Decisions"). The ten **CD records themselves are unchanged and still binding** — the observed reference behavior, the options, the proposed defaults, the blocks, and the closure evidence all stand as written. What changes is *where a policy lives, how it is expressed, and how it is tested*. The CD dispositions affected are named in §7.

The I0 record described `psxrt-compat` as "policy framework — all defaults per CD-01..CD-07; no policy activation (I5)". That framework is **retired as a framework**, and the crate it was built into is redirected: all eight policy modules plus the collecting `lib.rs` framework are deleted, their contents redistributed as runtime mechanisms, per-subsystem parameters, or documentation, and the crate's scope becomes the original-format writers it never contained. An earlier pass of this document said "four stay, four split"; that was the wrong question. The question is which of five categories each item belongs to (§3), and the answer for every item in `psxrt-compat` is *not* the one that crate answers. This document gives the disposition table (§5) and the migration path (§9).

## 1. What was wrong with the I0 framework

The I0 shape was: one module per policy; each policy enum carries one or more `pub const …: PolicyRecord` values (16 of them, in `LEDGER`); four of those policies also appear as fields of a `#[derive(Default)] Copy` struct `CompatPolicy` with a `reference_fidelity()` constructor. There is no lookup function, no `Feature` vocabulary, and no runtime dispatch of any kind — a consumer would have to receive a `CompatPolicy` and match on its fields by hand.

Four defects. Each is checked against the shipped source, and the first draft of this section mis-stated three of them, so the corrections are recorded here rather than quietly applied: the first draft described a `HashMap` lookup keyed by a `PolicyId`, an `Availability::Disabled` variant, and a 35-entry ledger. **None of those exist** — `Availability` has two variants (`Implemented`, `RecordedOnly`), `LEDGER` has 16, and the only map in the crate is a `BTreeMap` inside a test fixture parser. A criticism of a design that does not match the code is worse than no criticism, because it invites a fix to nothing.

1. **A record had no path to a consumer, and the design never named one.** `CompatPolicy` is read by exactly one test (`policy_ledger.rs`). That is not a bug in I0 — no renderer, no SPU model, and no ordering table existed yet to read it. It is a defect in the *shape*: the only way a subsystem could consume a policy was to take a `CompatPolicy` parameter, which puts a `psxrt-compat` dependency underneath `psxrt`, and `planning/01` §5 rule 1 forbids that. So the framework was unreachable *by construction*, not merely unused. What had to be decided before I5 was **who asks, and with what arguments** (ADR-010's backdoors), not how to widen the table.
2. **`Availability` describes the default, so it cannot express "both alternatives exist".** `Implemented` means *the default's mechanism exists and is exercised by tests*; `RecordedOnly` means nothing branches on the entry. There is no state for "the original behaviour is also buildable, and something selects between them" — which is the only state where a compatibility flag does anything. Compounding it, availability hangs off the *record*, while the knob hangs off `CompatPolicy`, and the two surfaces are unrelated by design (16 records, 4 fields — the crate doc says "the difference is the point", and for documentation it is). The consequence is that 12 records state a divergence with no way to select either side, and the test suite verifies *record integrity*, never *policy effect*.
3. **Three modules carried data-format facts next to policy.** `predictor.rs` holds seven XA layout constants (`SOURCE_RATE_HZ`, `HEADER_BYTES`, `CODING_INFO_OFFSET`, `PORTIONS_PER_SECTOR`, `PORTION_BYTES`, `SAMPLES_PER_SECTOR_LANE`, `MAX_BOUNDARY_LEAK_SAMPLES`); `rate_00.rs` holds a flag-word decoder (`translucency`, `page_translucency`, `flag_translucency`, the two shift constants, `NO_TRANSLUCENCY`); `display_clamp.rs` holds four display dimensions and `clamp_draw_width`. A file that is half format header and half policy cannot be tested as either, and it makes the *format* look optional: the XA sector geometry is not a thing anyone toggles. These are class **A** under the five-category rule (§5, §3).
4. **Structurally: one flat table over a 135-row checklist with no idea which of three different things a row was.** Several rows were never policies (§3), several are not compatibility at all (§2), and `battle_speed`-shaped rows would have sat beside GTE-precision-shaped rows if they had been added. The table had no notion of *who sets a knob and when*, which is the only thing that separates a player option from a compatibility override.

## 2. The three-level configuration model (ADR-004)

Three levels. The distinction is **who sets it and when**, not how important it is.

| Level | Name | Set by | Set when | Where defined | May a save file set it? |
| --- | --- | --- | --- | --- | --- |
| **L1** | engine configuration | the player, or a preset | before a campaign, and mid-campaign | `severedchains-sdk` `config` | yes — config is serialized with the save (CL-SAV-12) |
| **L2** | presentation / audio profile | the player, as a **whole profile** | at startup, or by an explicit mid-game profile change that reinitializes the affected subsystems | `severedchains` engine config, consumed by the backend | no |
| **L3** | compatibility override | the developer, at build time, or through a named engine profile | build, or startup before the subsystem initializes | the **consuming subsystem** (a `psxrt` module's parameter, or a profile in `severedchains` that sets several at once) — never `psxrt-compat` | no |

**The routing rule, in one line: "is this something the player configures?" → L1. "Does a whole presentation or audio mode have to change with it?" → L2. "Is it a per-subsystem mechanism choice?" → L3, placed with the subsystem that runs it.** "It is a compatibility concern" is not a routing answer — that phrase has been the source of three misplacements so far, and §3's placement test replaces it.

That is the minimum separation this project needs. It is not three configuration systems. It is **one configuration model with three levels**, distinguished by layer, default, and whether a player may set it (ADR-004) — a `bool` is insufficient because a flag cannot tell the reader whose behavior it is. It is *not* addressed by one shared `Feature` vocabulary: the earlier draft of this section said "one `Feature` vocabulary with explicit layers", and that is the registry shape §6 rejects. What survives is the three-way distinction, held in prose and in the profile enums.

Three consequences that are easy to get wrong, and were wrong before:

- **A player-facing option is not a compatibility policy.** `battle_speed` is L1 engine configuration (it is one of the reference's 88 registered config entries, and `Config.load()` clamps it). `renderer_profile` is L2. Neither is a `psxrt-compat` module.
- **L2 is selected as a whole profile**, because the presentation mode cannot be decided per-`TmdFormat` (ADR-007): the two presentation paths consume different geometry and different CLUT read paths, so a mode change forces different fixtures and different verification.
- **L1 lives in the SDK, not in `psxrt-compat` and not in `psxrt`.** The reference's config surface is 88 registered entries — `CoreMod` 80, `LodConfig` 7, `TurnOrderConfigs` 1 (`research/saves/02-config.md` §2.1, item D3, source-verified at reference revision `0c08c679b`). No evidence has been collected that any of them selects a GTE precision, an ordering-table mode, or an SPU model, and no other module defines a config registrar. So the L1/L3 separation here is a **design choice, not a reproduction**. If a later census finds a config entry that does select a model, §3's placement test decides where the mechanism goes — this sentence does not, and neither does a config entry.

## 3. Checklist disposition rule — five categories (ADR-005)

A checklist row, and every module that grew out of one, is exactly one of five things. **Classify before deciding where it goes**, and use the same five labels here and in §5's disposition table — the first pass of this document used a four-kind list here and a five-class list there, which guaranteed that some rows would be routed by whichever list happened to be nearer.

| Class | What it is | Where it goes |
| --- | --- | --- |
| **A — runtime mechanism** | a way the runtime does something: a calculation, an ordering, an evaluator, a long-lived piece of machinery with state, a representation that is read while a frame or a stream is produced | `psxrt` if it is a PSX platform service; the game subsystem (`severedchains::render`, `::audio`) if it is a presentation or transport choice; `psxrt-import` if it is a *decoder* of an original container |
| **B — configuration / policy selector** | the choice of which mechanism runs: an enum, a parameter, a preset discriminant | the subsystem that consumes it, as an explicit parameter that module declares. The **values** come from L1/L2 configuration. Never a cross-subsystem flag bag, and never in `psxrt-compat` |
| **C — research evidence** | what the original hardware did, and the confidence in that statement: the record, the dual-layer tag, the divergence note, the register pointer | documentation: the consuming module's doc header, `DIVERGENCE.md`, and the `planning/06` row. Never a compiled type whose only reader is a test |
| **D — original-format encoding** | produces, validates, or round-trips an original-format artifact, for a modder, a tool, or a fixture generator | `psxrt-compat`. This is the **only** class that makes the crate a crate |
| **E — obsolete** | neither: a placeholder, a duplicate of a fact already stated elsewhere, an abstraction whose consumer was never planned | retired |

**Three things that were filed wrongly, and what they now are.** They share one symptom — the same fact appearing as a format constant, a policy enum, and a doc claim in three places — and the fix is the same each time: name one owner per class.

1. **A hardware-derived data layout is not a compatibility decision** (class A, sometimes with a class-B selector on top of it). The TIM header layout, the 24-byte XA header (X1), the 8-byte vertex stride, the 4-bit/8-bit pixel index read, the SSHD container, the ANIM records: there is no "modern alternative" that produces the same bytes, so there is nothing to select. Their home is a representation module (`gpu::clut`, `spu::xa_adpcm`) and/or a decoder (`psxrt-import`). **Do not create a `psxrt-compat` module for a format** — a `compat::xa` module is a category error that survived in the earlier drafts, and the reason it survived is that "compatibility" was never split into its three kinds (planning/01 §2).
2. **A long-lived piece of machinery with threads or a device is a runtime service** (class A). `XaPlayer`, `VideoPlayer`, the FMV demux loop, the two audio threads, the frame pacer → the engine layer. **`Any AudioPlayer in psxrt is explicitly out of scope`** (planning/07 §4), and none of it is reverse conversion either.
3. **`files/` and `state_data/` are runtime storage** (class A, owned by the cache) — and the `CompatFlags::files_format` / `.state_format` flags were class E. What they were groping at is a *format version* (`VERSION = 5`) with a wipe-below rule, which is a storage concern with one correct answer at a time.

**The litmus test, in one question.** *Does this code produce, validate, or round-trip an original-format artifact?* If yes → class **D**, `psxrt-compat`. If it selects or performs how the game behaves → class **A** or **B**, the subsystem that runs it. If it records what the original did → class **C**, documentation. If none of those → **E**.

### Two further facts that constrain every dispatch

1. **Dispatch point.** **`Gpu` dispatches translucency at draw-command execution time; `TmdFormat` dispatches at decode time.** These are genuinely different points. One is a single enum carrying a TPage mode **plus** a flag-word mode; the other is a four-flag `TmdFormat`. They must not be forced into a shared `TmdMode`, and they must not be forced into a single "modern" name.
2. **`TmdFormat` is not a compatibility-policy type, even if a future policy references it.** It is a format discriminator in `psxrt-import`, **plus** a decode-time selection; and the modern path must also work when TMD is never involved at all. The `psxrt-compat::model` encoder consumes the same discriminator in the other direction — that is a class-D consumer of a class-A type, which is exactly the shape the crate is for.

## 4. The four-level record template (ADR-005)

Every class-C record carries five things. **The template carries the divergence documentation. It does not carry the implementation, and it is not compiled.**

| Field | Meaning | Why it is load-bearing |
| --- | --- | --- |
| `evidence` | the checklist row id + the confidence, as a **dual tag** — reference confidence **and** original confidence | the two are different questions; "the reference does X" does not imply "the original does X" |
| `layer` | `Psx` / `LodSpecific` / `ReferenceSpecific` | names whose behavior this is; the compatibility-exception list keys off this |
| `default` | which alternative ships when nothing is opted in | must be a real alternative that works, not a `None` sentinel |
| `knob` | the selector type and its alternatives | every alternative is unit-testable **without a GPU or audio device** |
| `divergence` | what is expected to differ, at what magnitude, and **the register id that would close it** | without the pointer, the divergence is folklore |

**Rejection criterion, stated so it cannot drift:** *a compatibility table that only records "Java did it this way" does not count as a compatibility layer.* A record whose `layer` is empty is not finished. A record whose `evidence` is `SourceVerified` on both halves is not finished — that tag says nothing.

**Retention.** Of the 16 records in the I0 `LEDGER`, the **information** is retained and the **table** is not. Evidence, layer, default, divergence note, and register pointer each move to a home appropriate to their kind: a module doc header, a profile entry in the engine crate, a format module's doc header, a traceability row. All sixteen are class **C**. `research/cross/02` remains the source of truth for the 135 rows; this document records only what each kind becomes.

## 5. Migration — module by module

Current `psxrt-compat` → destination, classified against the five kinds. This is the disposition of **all eight policy modules plus the framework in `lib.rs` that collects them**.

| Class (per §3) | Meaning | Destination |
| --- | --- | --- |
| **A** | runtime mechanism — an ordering, a precision, a clamp, a decode, an envelope, a data structure with behaviour | `psxrt`, or the game subsystem that executes it |
| **B** | configuration / policy selector — the enum or flag that *chooses* between mechanisms | the subsystem that consumes it, as an explicit parameter; the *choice of value* is engine configuration (L2) |
| **C** | research evidence — the record, the confidence, the divergence note, the register pointer | documentation: the module doc header, `DIVERGENCE.md`, the `planning/06` row |
| **D** | original-format encoding — produces an original-format artifact | `psxrt-compat` |
| **E** | obsolete infrastructure | retired |

**Result, stated before the table so the table cannot be misread: no module is class D, and therefore no module stays in `psxrt-compat`.** Eight modules, none of which encodes, writes, validates, or round-trips an original-format artifact. Six contain a selector enum, a layout fact, and a record; two (`blend_select.rs`, the `lib.rs` framework) contain only metadata. The toolchain modules that *do* qualify as class D — TIM emission, CTMD re-encoding, the XA sector writer, disc reinjection — are unbuilt and are what the crate is for (`planning/01` §4, TD-04).

| Current | What it actually contains | Class | Destination | Why |
| --- | --- | --- | --- | --- |

That is a mechanism with an observable effect, not an encoding. Verified: `SameZOrder` has no consumer outside `lib.rs`'s ledger and one assertion in `policy_ledger.rs` |

If a `B+F/4` decomposition is ever built it is a second `psxrt::blend` equation path with a `blend::Model` parameter — still not a `psxrt-compat` module |

When it is written it will be written in `psxrt`, and the enum will either be that module's parameter or nothing |

**Two facts that make the table executable rather than editorial.** Both were checked on 2026-11-15 against the shipped tree.

1. **Nothing consumes any of it.** Across `crates/`, `SameZOrder`, `GtePrecision`, `SweepEnvelope`, `VoiceCapacity`, `PredictorReset`, `clamp_draw_width`, `CompatPolicy` and `PolicyRecord` appear only in their own definitions, in `lib.rs`'s ledger and `CompatPolicy` struct, and in `tests/policy_ledger.rs`. There is no read of a policy from `psxrt/src`, and no `use psxrt_compat::…` anywhere in `psxrt`. The framework is unreachable in the literal sense: a consumer would have to be written first, and no milestone plans one.
2. **Three doc comments currently teach the wrong rule**, and they are the reason the correction has to reach `psxrt` and not only `psxrt-compat`: `psxrt/src/lib.rs:7` ("that choice is a policy toggle and lives in `psxrt-compat`"), `psxrt/src/rng/mod.rs:17` ("Choosing *what* to feed those arguments is policy and lives in `psxrt-compat`"), `psxrt/src/bpp.rs:50` ("Bits 5 and 6 are documented in `psxrt-compat::rate_00`"). The first two are corrected to name the subsystem that owns the choice; the third is correct in intent — the bits *are* documented there — and is redirected at the same time the decoders move.

**The replacement model.** Per-subsystem parameters with named consumers, plus one engine-level profile per family. `psxrt::gpu::SameZOrder`, `psxrt::gpu::OrderingStrategy`, `psxrt::gte::TransformPrecision`, `psxrt::spu::SweepMode`, `psxrt::spu::VoiceCapacity` are *mechanisms and their parameters*. `severedchains::render::profile::PresentationProfile` and `severedchains::audio::backend::AudioProfile` are where a **set** of those parameters is chosen together, and their values come from the game crate at boot. What does not exist, at any layer, is a cross-subsystem flag collection: not `CompatPolicy`, not `CompatFlags`, not a `psxrt::compat` module. The earlier "single ledger with string-`or`-enum-style id keys" and the earlier "a feature flag per module" are both retired.

## 6. `CompatPolicy`, `PolicyId`, and the ledger — what replaces them

- **`CompatPolicy` (the four-field `Copy` struct + `reference_fidelity()`): retired as a *shape*, kept as an idea.** Its idea — that the shipped default set and the reference-faithful set differ in exactly one field, and that a test holds that statement true — is the best thing in the I0 crate and moves to the per-subsystem matrix fixtures. What is retired is expressing the whole policy surface as one struct a consumer must receive wholesale.
- **`CompatFlags` is rejected, and so is the `psxrt::compat` module that was to hold it.** The first pass of this revision proposed a bitset of semantically named flags (`DISABLE_ORDERING_TABLE · LEGACY_3D_QUEUING · GTE_FIXED_POINT · SWEEP_ENVELOPE · PREDICTOR_PER_FILE · BLEND_DECOMPOSED · …`), resolved at startup. On inspection that is the same design error moved one directory up: it is still a cross-subsystem bag whose only coherent reader is "everything", it still has no answer to *who sets flag N and when*, and a bit that no code reads is a lie about a capability. It would also have re-created the forbidden edge in the other direction — a `psxrt`-resident flag bag that the engine addresses by name is a policy registry with a runtime host instead of a toolchain host. **Rejected on principle, with the rejection recorded so it is not re-proposed:** a generic compatibility policy registry, a global feature-flag bag, and any runtime-readable policy ledger.
- **What is used instead.** Two things, both smaller:
  1. **a parameter per decision, declared by the module that executes it** — `gpu::SameZOrder`, `gte::TransformPrecision`, `spu::SweepMode`, `spu::VoiceCapacity`. A parameter cannot be set for a subsystem that is not being run, it is visible in the signature of the thing that uses it, and its alternatives are unit-testable with no device (the §8 backdoor rule still applies to it).
  2. **a profile per family, in the engine** — `render::profile::PresentationProfile`, `audio::backend::AudioProfile`, each a small enum whose variants *supply a set of those parameters together*. This is where L2 lives. The game crate supplies the values at boot; a profile change reinitializes the affected subsystems.
- **`Feature` is a vocabulary of three parts** — the layer it belongs to, its default, and whether it may be user-configured. That vocabulary is realised **as documentation and as the profile enums**, not as a registry with string or enum ids, and not as a `bitflags` type. It does not need `Default` derived for convenience's sake.
- **`LEDGER` decomposition:** the 16 records regroup by *consumer*, not by directory: **7** rendering/presentation (same-z, the three display-clamp records, rate-00, the two blend records), **2** geometry transform (the two GTE records), **7** audio (the two sweep records, voice allocation, the four predictor records). Each group's records move to the **documentation of** the module that will consume them — its doc header, `DIVERGENCE.md` where there is a divergence, and its `planning/06` row. **These are record groups, not modules and not directories.** No `crates/psxrt/src/display/` directory is created and no `crates/psxrt/src/compat/` module is created; the grouping exists so that redistribution can be audited — every record must land somewhere named — not so that directories can be made.
- **`policy_ledger.rs` is not rewritten, it is replaced.** Its seven tests assert record integrity (every record names a real checklist row, a real register id, a non-empty divergence note). That is a documentation-integrity test wearing a Rust harness, and after the redistribution there are no records in Rust to check. Two things take its place: the per-subsystem matrix fixtures (which test *effect*, the thing §1 defect 2 says the ledger never tested), and **one new architectural guard** — a workspace test that fails if any runtime crate lists `psxrt-compat` as a dependency, or if any `psxrt` source file names `psxrt_compat`. That guard is the durable form of the rule this document exists to state.
- **`REMAP.md` is not one global file.** See planning/01 §6.5. The three `psxrt` doc comments listed in §5 are corrected in the same pass, because a comment that routes a reader to the wrong crate is worse than no comment: it is a citation of a claim the architecture has stopped making.

## 7. Where the ten CDs land

The **dispositions are unchanged** — same defaults, same knobs, same closure evidence, same status. What changed is the owner column: which crate holds the mechanism, and which holds the choice.

| CD | Row | Class | Level | Outcome of the revision |
| --- | --- | --- | --- | --- |
| CD-01 | G6 same-z | A | **L2 profile** (the presentation mode selects it) + a dev override | the LIFO/FIFO orderings are `psxrt::gpu` OT-replay strategies with a `gpu::SameZOrder` parameter; the value comes from `render::profile::PresentationProfile`. **Nothing lands in `psxrt-compat`.** A modern-path equivalent must also exist, or the knob is a knob and not a model |
| CD-02 | R4/Q-70 RNG seed | A | **L1 + dev** | **no change to the disposition, and no change of owner.** The seed source is a game-level choice about what to feed an injected stream; it lives with the state that seeds, and the dev `--seed` override stays behind the dev feature. `psxrt-compat` never held it and does not acquire it |
| CD-03 | T2 GTE precision | A | **L3**, with a **mandatory integer program** | the integer submap camera program is **built in `psxrt::gte`** because it has no clean modern equivalent, and `TransformPrecision` is that module's parameter (TD-22). The "modern default" principle **does not override** the T4 obligation, and the obligation is discharged by *building the program*, not by declaring an enum in a toolchain crate |
| CD-04 | G4 the 384→368 clamp | **A, with a B tail** | L2 profile | the clamp and the extents move to `psxrt::gpu`; the profile that enables them is L2. The two-distinct-368s note is preserved verbatim |
| CD-05 | G11 rate-00 | **A, with a B tail** | L3 | rate-00 → `B+F/2` stays **a compatibility escape hatch**: no clean modern default exists, so the mapping is implemented in the runtime (`psxrt::gpu::pixel`) and recorded in `DIVERGENCE.md`. The selector, when it is needed, names a *decode model*, not "emulation" |
| CD-06 | S7 sweep | A | L3 | unchanged disposition, new owner: the envelope evaluator is `psxrt::spu`, selected by `spu::SweepMode`. Default **on**, the reference gap not preserved |
| CD-07 | X6 predictor | A + format constants | L3 | `PredictorReset` becomes a `xa_adpcm` decoder parameter; the six format constants move to `psxrt::spu::xa_adpcm`, where the I1b encoder will read them too |
| CD-08 | C-01 dual opcode tables | not a policy — a **documentation obligation** | — | moves to `severedchains-sdk` `fate::binary`; the discrepancy stays preserved as data, with the per-opcode retail verification left open and asset-gated |
| CD-09 | Q-74 SFX tick quantization | **A**, mechanism and selector together | L3 policy **over** a runtime mechanism | the 8.0 ms SFX tick and the sample-accurate BGM are **runtime mechanisms** in `psxrt::spu` / `psxrt::audio`. Which one a reference layer uses is an `audio::backend::AudioProfile` choice; the evidence for the choice is recorded per layer in `research/audio/*`. **No `psxrt-compat` module is created for it** |
| CD-10 | Q-80 memcard shape | **A, as a format** | — | not a policy. A class-A file layout with an unresolved provenance question; its home is `severedchains-sdk::save` (read) and, if a writer is ever built, `psxrt-compat` (write) |

**Six items are deliberately *not* CD rows.** The modern presentation and audio defaults listed at `planning/04` I5b are numbered **MP-01…MP-06** (scene-queue ordering, the three logical layers, the HDR chain, explicit alpha and blend, the mask surface, the audio bus). They are model defaults of the modern path, not compatibility decisions, and giving them CD numbers would imply each one needs an original-behavior citation before it can be built. It does not. Where one of them has to *coexist* with a compatibility escape hatch (MP-04's explicit blend alongside the rate-00 mapping, MP-06's bus alongside the sweep envelope), the coexistence is stated in the I5b gate record.

## 8. Test backdoors (ADR-010)

**Compatibility policy modules remain testable without running the game, and without a GPU or audio device.** A module is still allowed to expose a way to apply the override directly to a context or a fixture.

Two backdoors, both **non-vtable**, both **test-only or tooling-only**:

1. a **direct predicate** taking the plain inputs the decision needs (no device, no engine context);
2. a **pure function** that applies the policy to a buffer or a fixture — e.g. the module transforms a `u32` buffer, or runs over a synthetic `files/` tree.

Both are permitted **even when they do not match the production dispatch path**, because their purpose is verification. They stay inside the module and are **documented as test-only**. A test backdoor is not a runtime service, must not become a hidden runtime plugin interface, and must not be a public API "just in case". The `PolicyEnv` concept from the earlier draft is allowed to return, **restricted to the tooling and test surfaces** — it is not a runtime dependency.

This is the explicit answer to "the compatibility layer shall be a non-public compatibility layer". Non-public means not *published to players*, not *unreachable from tests*.

## 9. Migration path

Four steps, ordered by when a consumer exists. Nothing here is a move of working code into a better directory; five of the nine files are deleted and their content is re-expressed where a reader will find it.

1. **I1a — `psxrt-compat` becomes a toolchain crate, and the policy scaffold comes out in the same milestone.** `psxrt-compat::container` (the MRG/BPE writers) is added; the eight policy modules and the `lib.rs` framework are deleted; the crate's `Cargo.toml` description, which currently advertises "Compatibility policy layer … as typed defaults with knobs", is rewritten to say what the crate does; `psxrt-compat`'s dependency on `psxrt` is dropped, and re-added per module only if an encoder turns out to need a runtime model. Doing the deletion and the first real module in one step is the point: a crate that contains both a toolchain module and a retired policy scaffold is a crate whose next contributor cannot tell which one it is. `psxrt`'s three doc comments (§5, fact 2) are corrected here.
2. **I1b — the class-D modules land.** `psxrt-compat::texture` (TIM emission, including the RGBA8 → 2-bit encodings), `psxrt-compat::model` (TMD / CTMD re-encoding), `psxrt-compat::audio` (XA encode, the sector writer, SSHD / SSSQ writers) are added beside `container`, and the two §5-class-D test hooks (`psxrt-compat` testing against `psxrt-import`'s decoders; `psxrt-import` synthesising fixtures) are wired as `dev-dependencies`. The six XA constants land in `psxrt::spu::xa_adpcm` **once**, read by both directions.
3. **I3 — the class-A representations land in `psxrt` with the modern default already in place.** `gpu::clut`, `gpu::pixel`, `spu::xa_adpcm`, `gpu` (the command vocabulary and the VRAM store), `audio::{device, transport}`. Where a class-A fact had a home in the deleted scaffold (the clamp, the extents, the flag-word decoder) it is written here from `research/cross/02` and the research doc, not copied from a file whose tests only proved the file agreed with itself. `policy_ledger.rs` is replaced here by the per-subsystem matrix fixtures plus the dependency-direction guard.
4. **I5a — the class-A *policies* activate against their model**, each as a parameter with a named consumer and its matrix fixture (planning/05 §5.3): same-z ordering, GTE precision with the mandatory integer camera program, the sweep envelope, voice capacity, the predictor reset, the blend model. A policy that never acquires a consumer is closed as class **E**, not left as a declaration.

**What is not done:** no register item is closed by this revision. The ten CDs keep their research statuses (`Open`, `Conflict`) and their closure evidence verbatim; the two dual-layer rows and CD-08's conflict status are preserved rather than resolved. Blast radius is unchanged — each CD blocks only its subsystem's *done* declaration, and a policy flip is a flip, not a rework. What *is* changed: the revision removes the arrangement that would have made a working game depend on a toolchain crate.
